# 04-技术选型

> 本文汇总广告投放执行 Agent 项目的整体技术选型，是后续系统设计、开发、部署和依赖安装的技术基线。
>
> 项目整体采用 **Python + FastAPI + Vue 3 + MySQL + Redis + Milvus + 百炼平台 + LangChain + LangGraph + MCP** 的技术体系，实现从投放策略生成、广告任务创建、实时监控、异常诊断、人工审批、动作执行到效果复盘的完整闭环。

# 2. 整体技术架构

系统整体可以划分为以下几层：

```text
Vue 3 前端
    ↓
FastAPI REST API
    ↓
Service 业务服务层
    ↓
LangGraph Agent 编排
    ↓
┌──────────────┬──────────────┬──────────────┐
│ LangChain/LLM│ Milvus/RAG   │ MCP Tools    │
│ 百炼大模型    │ 向量召回      │ 广告平台能力   │
└──────────────┴──────────────┴──────────────┘
    ↓
MySQL / Redis / Milvus
```

其中：

- **FastAPI** 负责 Web API 和业务入口。
- **Service** 负责普通业务逻辑和基础设施调用。
- **LangGraph** 负责跨步骤的投放生命周期编排。
- **LangChain** 负责模型调用、结构化输出和知识处理。
- **MCP** 负责广告平台等外部能力的工具边界。
- **MySQL** 保存业务事实和历史记录。
- **Redis** 保存实时态、队列和临时状态。
- **Milvus** 保存向量数据并完成语义召回。

# 3. 后端技术选型

## 3.1 Python 3.12+

后端使用 Python 3.12+。

选择 Python 的核心原因是项目主要围绕 AI Agent 展开，LangChain、LangGraph、DashScope、MCP 等核心组件均拥有成熟的 Python 生态。

同时 Python 在以下场景实现成本较低：

- LLM 调用
- Agent 编排
- 向量检索
- 数据处理
- 定时任务
- MCP Server
- 文档解析

---

## 3.2 FastAPI

Web 框架采用 FastAPI。

主要原因：

1. 原生支持异步，适合 LLM、向量数据库、MCP 等 IO 密集调用。
2. 基于 Pydantic 实现请求和响应校验。
3. Pydantic Schema 可以同时用于 Agent Structured Output。
4. 自动生成 OpenAPI 文档，方便前后端联调。
5. 与 Python AI 生态集成成本较低。

---

## 3.3 SQLAlchemy 2.0

数据库 ORM 使用 SQLAlchemy 2.0。

主要使用：

```text
FastAPI
    ↓
AsyncSession
    ↓
SQLAlchemy
    ↓
MySQL 8.0
```

选择原因：

- 支持异步数据库访问。
- 声明式模型配合类型提示，表结构清晰。
- 可以支撑项目中的复杂业务关系。
- 完整支持 MySQL 8.0。

# 4. 后端工程分层

后端工程技术标识：

```text
ad-agent-backend
```

推荐目录职责如下：

| 层 | 目录 | 职责 |
|---|---|---|
| 路由层 | `routers/` | HTTP 请求、参数校验、调用 Service |
| 服务层 | `services/` | 业务逻辑、数据读写、缓存、Agent 调用 |
| 模型层 | `models/` | SQLAlchemy 数据模型 |
| Schema 层 | `schemas/` | Pydantic 请求/响应和结构化输出 |
| Agent 层 | `agent/` | LangGraph 状态、节点和工作流 |
| MCP 层 | `mcp/` | 模拟广告平台 MCP Server |
| 定时任务 | `tasks/` | 指标拉取、异常扫描、超时提醒 |
| 基础设施 | `config.py` 等 | 数据库、Redis、Milvus、配置 |

基础请求链路：

```text
前端
 ↓
FastAPI Router
 ↓
Pydantic 参数校验
 ↓
Service
 ↓
数据库 / Redis / Milvus / Agent / MCP
 ↓
统一响应
```

各层保持职责单一，避免将数据库、Agent、MCP 和 HTTP 逻辑混写。

# 5. API 设计约定

全项目 API 基础前缀统一为：

```text
/api/v1
```

例如：

```http
GET /api/v1/campaigns
```

统一返回：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

其中：

- `code = 0` 表示成功。
- 非 `0` 表示业务错误。
- 实际业务内容统一放入 `data`。

# 8. Redis：实时状态与队列

Redis 7.2 不作为核心业务事实存储，而主要承担实时态和临时状态。

主要包括四类用途：

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 实时监控指标 | Hash + ZSet | 最新指标和时间窗口数据 |
| 投放状态 | String / Hash | 当前投放状态、扫描任务状态 |
| 审批和执行 | List + Hash | 审批上下文、动作执行队列 |
| 去重 | String | 异常重复检测 |

例如同一广告组在短时间内连续产生同一种异常时，通过 Redis 去重 Key 避免重复生成多条异常。

# 9. 实时指标存储策略

实时指标采用：

```text
广告平台
   ↓
APScheduler 定时拉取
   ↓
MCP get_ad_metrics
   ↓
Redis
   ↓
实时监控页面
   ↓
周期性落 MySQL
   ↓
趋势分析 / 基线计算 / 复盘
```

即：

> **先写 Redis，再落 MySQL。**

Redis 用于快速查询最新状态，MySQL 用于历史分析。

实时监控看板不直接对 MySQL 做大量实时聚合，以避免影响响应速度。

```text
 ↓

 ↓

```

## 10.2 相似异常召回

```text

 ↓

 ↓
历史异常案例
 ↓

 ↓

```

## 10.3 相似干预案例召回


# 15. Human-in-the-loop

项目中的高风险操作不能完全交给 Agent 自动执行。

主要设置两个人工确认点：

1. **初始策略确认**
2. **高风险广告操作审批**

LangGraph 使用：

```python
interrupt()
```

暂停状态机。

审批完成后：

```python
Command(resume=...)
```

恢复。

示意：

```python
from langgraph.types import interrupt, Command

decision = interrupt({
    "action_request": {
        "action": "pause_ad_group",
        "args": {}
    },
    "description": "广告组消耗过快且有效线索率下降，建议暂停"
})
```

审批完成：

```python
graph.invoke(
    Command(
        resume={
            "approved": True,
            "approver_id": 1
        }
    ),
    config={
        "configurable": {
            "thread_id": campaign_id
        }
    }
)
```

项目以：

```text
thread_id = campaign_id
```

作为每个活动工作流实例的主要标识。

配合 Checkpointer 保存 LangGraph 状态，实现审批中断后的恢复。

# 17. 为什么选择 MCP

广告平台工具有两个候选实现。

| 方案 | 优点 | 问题 |
|---|---|---|
| LangChain Tool | 实现简单 | 平台代码与 Agent 强耦合 |
| MCP | 独立协议边界 | 多一层工具服务 |

本项目选择 MCP。

核心原因是：

```text
Agent
 ↓
MCP Protocol
 ↓
ad-platform-mock
```

未来切换真实广告平台时：

```text
Agent
 ↓
MCP Protocol
 ↓
真实广告平台 Adapter
```

只需要修改 MCP Server 的内部实现。

Agent、LangGraph 和业务 Service 不需要理解具体平台 API。

因此 MCP 在项目中本质承担：

> **Agent 与外部业务系统之间的协议隔离层。**

后续 CRM、素材库等能力同样可以沿用这一模式。

```text
Redis
```

# 19. AI 能力方向

项目主要涉及四类 AI 能力。

| 能力 | 项目中的实现 |
|---|---|
| Agent / Tool Execution | Agent 调用 MCP 执行广告动作 |
| Workflow Orchestration | LangGraph 编排广告投放生命周期 |
| RAG | 知识文档、策略依据、异常案例召回 |
| Recommendation / Matching | 相似活动、相似异常、相似案例匹配 |

---

## 19.1 Agent / Tool Execution

主要处理：

- 工具调用
- 工具权限
- 人工确认
- 执行失败处理
- 执行记录
- 动作回滚

主要对应：

```text
广告任务创建
动作执行
```

---

## 19.2 Workflow Orchestration

通过 LangGraph 管理：

- 节点顺序
- 状态流转
- 循环
- 条件路由
- Human-in-the-loop
- Checkpoint
- 中断恢复

对应整个广告投放生命周期。

---

## 19.3 RAG

主要用于：

- 渠道规则检索
- 平台政策检索
- 历史策略依据召回
- 异常案例召回
- 复盘案例召回

# 20. 不引入 MongoDB

本项目不使用 MongoDB。

原因：

1. 核心业务数据结构明确，适合关系数据库。
2. JSON 等半结构化字段可以直接使用 MySQL JSON。
3. 向量数据已经由 Milvus 保存。

因此没有必要额外维护文档数据库。

---

# 21. 不引入图数据库

本项目不使用 Neo4j 等图数据库。

原因：

- 不需要复杂关系网络遍历。
- 不需要知识图谱路径推理。
- 用户角色权限使用 MySQL 关系表即可。
- 相似关系由 Milvus 完成。

因此图数据库没有明显收益。

---

# 22. 不引入 RAGFlow

项目采用：

```text
LangChain Loader
 ↓
文本切片
 ↓
百炼 Embedding
 ↓
Milvus
```

已经覆盖当前 RAG 需求。

RAGFlow 会额外引入 Elasticsearch、MinIO 等基础设施，与现有 Milvus 和 Embedding 能力重叠。

因此本期不引入 RAGFlow。

---

# 23. 不引入实时流式计算引擎

本项目不使用：

- Kafka Streams
- Flink
- Spark Streaming

原因是当前系统主要用于单机项目和业务演示，不存在大规模广告事件流处理需求。

实时监控采用：

```text
APScheduler
+
MCP
+
Redis
```

实现近实时数据拉取和聚合，可以满足当前需求，同时显著降低开发和运维复杂度。

# 26. 最终技术栈

最终项目技术栈可概括为：

```text
Frontend
Vue 3
Vite
Element Plus
Vue Router
Pinia
Axios
ECharts
dayjs

Backend
Python 3.12+
FastAPI
Pydantic
SQLAlchemy 2.0

MCP Python SDK

阿里云百炼
LLM

Storage
MySQL 8.0
Redis 7.2
Milvus 2.6.17

Mock Platform
ad-platform-mock
```

整体设计原则为：

> **MySQL 管业务事实，Redis 管实时状态，Milvus 管语义召回；LangChain 管模型能力，LangGraph 管业务流程，MCP 管外部工具边界，FastAPI 管 Web 服务入口。**

通过这种职责拆分，使广告投放 Agent 的业务流程、AI 推理、外部平台调用和数据存储相互解耦，为后续从模拟广告平台迁移到真实广告平台保留清晰的扩展边界。
